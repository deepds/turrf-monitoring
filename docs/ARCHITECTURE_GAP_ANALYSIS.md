# Architecture Gap Analysis

**Дата:** 07.08.2026
**Сравнивается:** архитектура v1 против требований SCOPE-R 1.0

---

## 1. Целевые слои и где проходят границы

```text
Sources → Connectors → Raw → Normalization → Offer → Market Snapshot
       → Selection → Aggregation → Calculation → Data Mart → REST API → React Dashboard
```

Границы, которые нельзя размывать, и как они удерживаются в v2:

| Правило | Как удерживается механически |
|---|---|
| Коннектор не знает бизнес-методику | Коннектор возвращает `ProviderOffer` с наблюдаемыми признаками; он не имеет доступа к `MethodologyProfile` — профиль просто не передаётся в коннектор |
| Calculation Engine не знает source-specific деталей | `engine/selection.py` оперирует `Candidate` с полями `transport` / `property_info`; имён полей Туту или РЖД в нём нет |
| Source-specific поля остаются внутри коннектора | Всё неизвестное складывается в `source_metadata` и в отбор не попадает |
| Фронтенд не содержит расчётной логики | Проверяется воротами публикации: если у метрики с данными пуст `median`, `min` или `confidence_level`, снимок не публикуется — фронтенду пришлось бы это досчитать |

## 2. Разрывы v1 → v2

### 2.1. Наблюдение и расчёт разделены, но решение об исключении лежало не там

**Было.** Отбор в v1 фильтровал список: непрошедшее предложение исчезало из
выборки. Открыть цену и увидеть, что именно не попало в расчёт и почему, было
нечем.

**Разрыв.** SCOPE-R P19 требует `exclusion_reason` для каждого исключённого
предложения и запрещает физическое удаление.

**Стало.** Отбор возвращает `Decision` на каждое предложение. Решения пишутся в
`metric_offer_links` с флагом `is_included` и обязательной причиной. Причина —
свойство **расчёта**, а не наблюдения: при другой методике то же предложение
может войти в выборку.

### 2.2. Сценарий против детерминированной матрицы

**Было.** 1703 сценария в CSV, редактируемые пользователем.

**Разрыв.** Вторая задача наблюдает фиксированный рынок. План обязан строиться
детерминированно и быть проверяемым.

**Стало.** `planner/matrix.py` — чистая функция от даты снимка, справочника и
горизонта. Отпечаток плана (`plan_digest`) фиксирует состав: одинаковый вход
обязан давать побайтово одинаковый набор наблюдений. Дубли `job_key` внутри
плана поднимают исключение — совпадение ключей означало бы, что два разных
наблюдения пишутся в одну строку и одно теряется молча.

### 2.3. Круговой авиатариф и плечо ЖД

**Было.** Круговой ЖД собирался как cartesian product поездов; авиа — из двух
односторонних поисков.

**Разрыв.** SCOPE-R S3.2 запрещает подменять round-trip суммой двух one-way;
P9.2 требует наблюдать ЖД плечом.

**Стало.** ЖД — `RailQuery` на одно плечо и одну дату; блок «Куда ехать»
складывает **две отдельно наблюдавшиеся метрики** и подписывает это словами.
Авиа — `search_avia` с `return_date`, то есть настоящий круговой тариф на
конкретную пару дат. Флага, разрешающего собрать круговой тариф из
односторонних, в профиле нет намеренно.

### 2.4. Диспетчеризация

**Было.** Пачка мониторинга диспетчеризовала дочерние задачи и не отмечала
прогресс; 1703 сценария диспетчеризовались за минуты, а собирались часами, и
прогон объявлял зависшим сам себя.

**Разрыв.** SCOPE-R P3 требует rate-aware диспетчер, учитывающий источник,
темп, размыкатель, бюджет и остаток времени до SLA.

**Стало.** Диспетчеризация внутри задачи: пачка наблюдений исполняется одним
воркером тремя фазами. Лимитер темпа и размыкатель — общие на процесс
(`TRANSPORT_POOL`), иначе два потока со своими счётчиками дали бы вдвое больший
фактический темп. Состояние наблюдения выводится из его попыток, а не
записывается по ходу дела: после досбора у наблюдения несколько попыток, и итог
определяется всей их совокупностью.

### 2.5. Витрина считалась на лету

**Было.** `dashboard.py` (50 КБ) агрегировал при каждом запросе.

**Разрыв.** Блок «Куда ехать» — это 20 маршрутов × 435 пар дат × 2 транспорта ×
3 категории = до 52 200 комбинаций.

**Стало.** `trip_cost_mart` материализуется расчётом. Строка витрины хранит
идентификаторы метрик-составляющих, поэтому провенанс поездки ведёт через них к
предложениям. Неполная строка перечисляет, чего не хватило: пустая клетка
обязана объяснять себя.

### 2.6. Демонстрационные данные

**Было.** Два синтетических источника (`sandbox_alpha`, `sandbox_beta`) со
своим форматом.

**Разрыв.** SCOPE-R P23 запрещает использовать старый seed как acceptance
evidence и требует Golden Dataset на записанных ответах.

**Стало.** `connectors/replay.py` генерирует и воспроизводит ответы **в форме
настоящего источника**, а разбирает их боевым парсером. Один механизм
обслуживает и Golden Dataset, и демонстрацию без сети. Снимок помечается
`is_synthetic`, витрина показывает красный баннер, а `latest_published`
синтетические снимки не выбирает.

## 3. Требования SCOPE-R и их реализация

| Требование | Где реализовано |
|---|---|
| Market Snapshot неизменяем как наблюдение | Повторный сбор за ту же дату создаёт новый `attempt_no`, а не переписывает снимок |
| CalculationRun неизменяем | Новый расчёт создаёт новый Run; прежний помечается `is_active=false` и остаётся |
| Provenance обязателен | `metric_offer_links` → `offers` → `raw_responses` → файл с хешем содержимого |
| No silent failure | Каждая попытка оставляет `SourceAttempt` с конечным исходом; ворота публикации ловят наблюдения, завершённые без единой записи об обращении |
| `NO_MARKET != technical failure` | Отдельный статус наблюдения, засчитывается в завершённые, не попадает в дыры, не вызывает бесконечный досбор |
| Сеть вне долгой транзакции | Три фазы; в план уходят значения, а не ORM-объекты |
| Partial сохраняется | Мягкий бюджет останавливает обход, собранное пишется, наблюдение помечается `PARTIAL` |
| Фронтенд без бизнес-расчёта | Ворота `PUBLICATION_VALIDITY` проверяют полноту DTO машинно |
| Пороги версионируются | Все — в `catalog/data/profiles/*.yaml`; хеш содержимого фиксируется при регистрации, правка активной версии запрещена |
| Исторические raw / Offers защищены | Ретеншен удаляет только тела ответов; метаданные, Offers и метрики не удаляются |

## 4. Что осталось нерешённым

| Разрыв | Статус | Комментарий |
|---|---|---|
| Лимитер темпа общий на **процесс**, не на кластер | Открыт | При горизонтальном масштабировании на несколько узлов нужен общий счётчик в Redis. Пока сбор идёт с одного узла, разрыва нет |
| РЖД не измерен под нагрузкой | Открыт | Замер выполняется на узле сбора; исходные значения консервативны |
| Soak-прогон многочасовой нагрузки | Открыт | Все замеры — секунды и минуты. До эксплуатации обязателен |
| Ручная сверка контрольных цен с сайтами | Частично | Дип-линк на предложение выводится в детализации цены; сама сверка — операционная процедура, описана в `RUNBOOK.md` |
