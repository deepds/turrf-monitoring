# Архитектура

**Версия:** 2.0
**Дата:** 07.08.2026

---

## 1. Одно предложение

Ночью система заново измеряет рынок по детерминированной матрице из 15 840
логических наблюдений, сохраняет исходные ответы источников, нормализует их в
Offers, применяет версионируемую методику и к 10:00 MSK публикует витрину, в
которой любая цифра раскрывается до конкретного предложения конкретного
источника.

---

## 2. Слои и границы

```text
Sources → Connectors → Raw → Normalization → Offer → Market Snapshot
       → Selection → Aggregation → Calculation → Data Mart → REST API → React Dashboard
```

Четыре границы, которые нельзя размывать, и как каждая удерживается
механически, а не соглашением:

| Граница | Чем удерживается |
|---|---|
| Коннектор не знает бизнес-методику | Профиль методики физически не передаётся в коннектор |
| Движок не знает source-specific деталей | `engine/` оперирует `Candidate`; имён полей Туту и РЖД в нём нет |
| Source-specific поля остаются в коннекторе | Всё неизвестное складывается в `source_metadata` и в отбор не попадает |
| Фронтенд не считает бизнес-метрики | Ворота публикации проверяют полноту DTO машинно: пустая медиана у метрики с данными блокирует снимок |

## 3. Три уровня данных

```text
НАБЛЮДЕНИЕ                          РАСЧЁТ                     ВИТРИНА
market_snapshots                    calculation_runs           trip_cost_mart
  └ collection_plans                  └ calculated_metrics        индексы над
  └ collection_jobs                      └ metric_offer_links      метриками
      └ source_attempts
          └ raw_responses
          └ offers
```

**Наблюдение неизменяемо.** Повторный сбор за ту же дату создаёт новый
`attempt_no`, а не переписывает снимок: «вчерашняя картина» обязана остаться
такой, какой её видели вчера.

**Расчёт неизменяем.** Новый `CalculationRun` не трогает прежний — на него
ссылаются уже показанные цифры.

**Решение об исключении предложения — часть расчёта, а не наблюдения.** Оно
живёт в `metric_offer_links`, поэтому при смене методики то же предложение
может войти в выборку, а наблюдение останется прежним.

## 4. Как идёт суточный цикл

```text
план → первичный сбор → анализ покрытия → досбор дыр
     → расчёт → ворота качества → финализация снимка
```

### 4.1. План

Матрица — чистая функция от даты снимка, справочника городов и горизонта.
Отпечаток плана (`plan_digest`) фиксирует состав: одинаковый вход обязан давать
побайтово одинаковый набор наблюдений. Совпадение `job_key` внутри плана
поднимает исключение — оно означало бы, что два наблюдения пишутся в одну
строку и одно теряется молча.

### 4.2. Исполнение: три фазы

```text
plan     короткая транзакция: задания → значения
execute  транзакции нет: HTTP, ожидание темпа, бюджет времени
persist  короткая транзакция: запись собранного
```

Разделение поставлено по инциденту: сбор шёл внутри одной транзакции, и
ожидание лимита темпа держало `idle in transaction` по шестнадцать минут, за
которыми вставала вся база.

В план уходят **значения, а не ORM-объекты**: ленивое поле отсоединённого
объекта открыло бы новую транзакцию ровно там, где мы от неё уходим.

Падение воркера во второй фазе безопасно: терять нечего, кроме самих
обращений, а задания попадут в досбор.

### 4.3. Предохранители

| Предохранитель | Против чего |
|---|---|
| Лимитер темпа (скользящее окно, общий на процесс) | Залп из тысяч наблюдений источник не держит |
| Размыкатель цепи | После серии отказов перестаём спрашивать вовсе |
| Мягкий бюджет времени (240 с при жёстком 300 с) | Жёсткий обрыв уничтожает уже собранное |
| Бюджет наблюдения ≤ остаток бюджета пачки | Одно затянувшееся наблюдение не съедает пачку |

### 4.4. Досбор

Штатный шаг, а не аварийная мера. Дырой считается **только техническое**:
`TIMEOUT`, `RATE_LIMITED`, `SCHEMA_ERROR`, `TRANSPORT_ERROR`, `CIRCUIT_OPEN`,
`BUDGET_EXHAUSTED`, `FAILED`, а также наблюдения, до которых сбор не дошёл.

`NO_MARKET` дырой не является: «предложений нет» — ответ о рынке. Досбирать
Самару — Казань, где прямого сообщения не существует, значило бы тратить
обращения впустую каждую ночь.

Досбор идёт с солью в ключе идемпотентности: без неё повторное исполнение той
же области молча вернуло бы прежний результат.

## 5. Идентификаторы

Три ключа, которые легко перепутать:

| Ключ | Что различает | Где применяется |
|---|---|---|
| `job_key` | Что наблюдается внутри снимка, с абсолютными датами | Уникальность плана |
| `series_key` | Тот же ряд между снимками: даты заменены смещением от D | Исторические графики |
| `idempotency_key` | Что именно исполняется: снимок + источник + область + соль | Повторы и досбор |
| `fingerprint` | Строку источника: тарифные варианты одного объекта | Различение предложений |
| `equivalence_key` | Физический объект рынка: рейс, поезд + класс, отель | Схлопывание тарифной сетки |

## 6. Очереди и воркеры

| Контейнер | Очереди | Роль |
|---|---|---|
| `worker` | `collect`, `compute` | Всё длинное и сетевое |
| `worker-service` | `maintenance`, `ondemand` | Обслуживание и запросы пользователя |

Второй свободен по построению. Один воркер, обслуживающий все очереди сразу,
не выполняет собственного лечения: забитый сбором пул не запускает ни сторожа,
ни детектор застоя, ни досбор.

Проверка живости спрашивает не «отвечаешь ли ты», а **разбирается ли очередь**:
`celery inspect ping` отвечает из главного процесса и проходит исправно тогда,
когда все процессы пула заняты намертво.

## 7. Хранение

| Что | Где | Почему |
|---|---|---|
| Нормализованные сущности, метрики, витрина | PostgreSQL | Источник истины |
| Тела сырых ответов | Файловое хранилище, gzip, хеш в имени | Их десятки тысяч в сутки и до полумегабайта каждый |
| Метаданные сырых ответов | PostgreSQL | Провенанс и сверка хеша |
| Справочники и профили методики | YAML в образе + реплика в базе | Витрина и экспорт самодостаточны |

Ретеншен удаляет **только тела** ответов, через 45 суток. Метаданные, Offers и
метрики не удаляются никогда: без них опубликованную цифру нельзя объяснить.

## 8. Витрина

`trip_cost_mart` материализуется расчётом, а не считается на лету: блок «Куда
ехать» — это до 52 200 комбинаций маршрута, дат, транспорта и категории.

Строка витрины хранит идентификаторы метрик-составляющих, поэтому провенанс
поездки ведёт через них к предложениям. Неполная строка перечисляет, чего не
хватило: пустая клетка обязана объяснять себя.

---

## 9. Что удерживает систему от молчаливой ошибки

| Свойство | Механизм |
|---|---|
| Нет молчаливого пропуска источника | Каждая попытка оставляет `SourceAttempt`; ворота ловят наблюдения без единой записи |
| Отсутствие рынка отличимо от сбоя | Отдельный статус, отдельная причина, отдельное поведение досбора |
| Обрезанная выборка видна | `is_partial` + причина + запрет на HIGH + предупреждение на витрине |
| Исключённое предложение объяснимо | Обязательная причина в связи метрика↔предложение |
| Методика воспроизводима | Версия неизменяема, хеш содержимого фиксируется, Golden Dataset обязателен |
| Витрина не ходит в источники | Архитектурно: сервисы витрины не имеют доступа к коннекторам; проверяется тестом |
| Вчерашние данные не выдаются за сегодняшние | `is_fallback` в контексте + баннер на каждом экране |
| Демонстрационные данные не выдаются за рынок | `is_synthetic`, красный баннер, исключение из `latest_published` |
