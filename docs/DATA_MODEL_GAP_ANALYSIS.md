## 1. Три уровня, которые не смешиваются

| Уровень | Таблицы | Свойство |
|---|---|---|
| **Наблюдение** | `market_snapshots`, `collection_plans`, `collection_jobs`, `source_attempts`, `raw_responses`, `offers`, `snapshot_source_results` | Неизменяемо после закрытия снимка |
| **Расчёт** | `calculation_runs`, `calculated_metrics`, `metric_offer_links` | Новый расчёт создаёт новые строки, старые не трогает |
| **Витрина** | `trip_cost_mart` + индексы над метриками | Производная, пересобирается расчётом |
| **Справочники** | `cities`, `sources`, `methodology_profiles` | Реплика YAML в базе: витрина и экспорт самодостаточны |

## 2. Ключевое отличие от v1: где живёт решение об исключении

```text
v1:  offers.is_selected, offers.exclusion_reason
v2:  metric_offer_links.is_included, metric_offer_links.exclusion_reason
```

**Почему это принципиально.** Исключение — вывод методики, а не свойство
рынка. При пересчёте другой версией то же предложение может войти в выборку. В
v1 пересчёт переписывал бы поля наблюдения; в v2 он создаёт новый набор связей,
а наблюдение остаётся тем, чем было.

Побочное следствие: сравнение двух версий методики на одном снимке становится
запросом, а не отдельной механикой.

## 3. Сущности

### 3.1. `market_snapshots`

Ключ `(snapshot_date, attempt_no)`. Повторный сбор за ту же дату — новый
`attempt_no`, а не перезапись: наблюдение неизменяемо, и «вчерашняя картина»
обязана остаться такой, какой её видели вчера.

`is_synthetic` — снимок, собранный воспроизведением. `latest_published`
такие снимки не выбирает: расчётная величина, выданная за наблюдаемую цену,
— именно то, что запрещено.

### 3.2. `collection_jobs`

Плоские колонки, а не только JSON:

```text
origin_code, destination_code, city_code,
service_date, return_date, check_in, check_out,
stars, day_offset, nights
```

Причина утилитарна: запрос «медиана Москва → Сочи на 20 августа» не должен
разбирать JSON на миллионе строк. `params` JSONB остаётся для полноты.

Два ключа с разным смыслом:

* `job_key` — что наблюдается **внутри снимка**, включая абсолютные даты;
* `series_key` — тот же логический ряд **между снимками**: абсолютные даты
  заменены смещением от даты снимка, поэтому «плечо Москва → Сочи на D+14»
  сопоставимо между днями. Ось исторических графиков строится по нему.

### 3.3. `source_attempts`

Уникальность по `idempotency_key`, который включает область исполнения
(`PRIMARY` / `RECOVERY` / ручной повтор) и соль. Без области исполнения досбор
молча возвращал бы результат планового прогона — дефект v1, стоивший потерянных
ночей.

`fetched_at` отдельно от `requested_at`: свежесть считается от факта получения.
`total_matched` — сколько объектов насчитал источник; `NULL` означает «не
сообщил» и отличается от нуля.

### 3.4. `offers`

`CHECK (price > 0)` на уровне базы: неположительная цена не должна существовать
физически.

Два разных отпечатка:

* `fingerprint` — строка источника; различает тарифные варианты одного объекта;
* `equivalence_key` — физический объект рынка (рейс, поезд + тип вагона, отель).
  По нему схлопывается тарифная сетка.

Ключ эквивалентности включает код источника: цена одного поезда у Туту и у РЖД
— **два наблюдения разных продавцов**, а не дубликат.

`validation_flags` — отметки нормализации. Они не удаляют предложение: решение
принимает методика.

### 3.5. `calculated_metrics`

`per_source` хранит медиану по каждому источнику отдельно — расхождение обязано
быть видно, а не только замечено.

`is_no_market` + `no_market_reason`: отсутствие рынка — это метрика без цены, а
не отсутствие метрики. Иначе пустая клетка неотличима от несобранной.

### 3.6. `trip_cost_mart`

Витрина «Куда ехать». `transport_metric_ids` и `accommodation_metric_id`
ведут провенанс поездки к составляющим. `missing_components` перечисляет,
чего не хватило.

## 4. Индексы

56 индексов. Ключевые и почему они существуют:

| Индекс | Зачем |
|---|---|
| `ix_collection_jobs_route (family, origin_code, destination_code, service_date)` | Выборка ряда графика ЖД |
| `ix_collection_jobs_hotel (family, city_code, check_in, stars)` | Выборка ряда графика проживания |
| `ix_collection_jobs_series (series_key, snapshot_id)` | Исторический ряд одного наблюдения между снимками |
| `ix_metrics_route`, `ix_metrics_hotel` | Те же выборки на уровне расчёта |
| `ix_trip_cost_lookup (run, origin, departure, return, mode, stars)` | Один запрос блока «Куда ехать» |
| **`ix_offers_raw_response_id`** | **`ON DELETE SET NULL` без индекса делал удаление квадратичным: на 6 234 удаляемых строки СУБД просматривала 358 801 предложение — 20 минут без движения** |
| `ix_offers_equivalence (job, source, equivalence_key)` | Схлопывание тарифной сетки и контроль дублей |
| `ix_metric_offer_links_metric_included` | Детализация цены: включённые отдельно от исключённых |
| `ix_source_attempts_fetched_at`, `ix_raw_responses_fetched_at` | Ретеншен и расчёт свежести |
| `uq_source_attempts_idempotency_key` | Идемпотентность |

## 5. PostgreSQL против SQLite

| Что | PostgreSQL | SQLite | Как закрыто |
|---|---|---|---|
| JSON | `JSONB` с индексами | `JSON`-текст | `JSONType = JSON().with_variant(JSONB, "postgresql")` |
| Время с зоной | `timestamptz` | зона теряется | Тип `UtcDateTime` приводит обе стороны к UTC явно |
| `BigInteger` PK | `bigserial` | нет автоинкремента на BIGINT | `.with_variant(Integer, "sqlite")` |
| Конкурентная запись | MVCC | блокировка файла | Конкурентность проверяется только в PostgreSQL-наборе |
| `idle_in_transaction_session_timeout` | есть | нет | Задаётся в `connect_args`; предохранитель от повисшей транзакции |
| `ALTER` с именованными ограничениями | есть | нужен batch-режим | `render_as_batch` в Alembic для SQLite |

**SQLite допустим только там, где не проверяется поведение PostgreSQL.**
PostgreSQL-набор обязателен и не заменяется.

## 6. Объёмы и ретеншен

| Таблица | Строк в сутки | За 30 суток |
|---|---:|---:|
| `collection_jobs` | 15 840 | 475 200 |
| `source_attempts` | ≈ 16 400 | ≈ 492 000 |
| `raw_responses` | ≈ 78 000 | ≈ 2,3 млн |
| `offers` | 0,4 … 5,2 млн | до 156 млн |
| `metric_offer_links` | столько же | столько же |
| `calculated_metrics` | 15 840 | 475 200 |
| `trip_cost_mart` | до 52 200 | до 1,6 млн |

**Что удаляется:** только тела сырых ответов, через 45 суток
(`tmo.purge_raw`). Метаданные `raw_responses`, `offers`, метрики и связи не
удаляются никогда — без них опубликованную цифру нельзя объяснить.

**Что рекомендуется при выходе за 30 суток истории:** партиционирование
`offers` и `metric_offer_links` по `snapshot_id` диапазонами. Не сделано сейчас
намеренно: партиционирование до появления объёма усложняет миграции без выгоды.

Правила удаления, вынесенные из v1 дословно:

* отбор строк для удаления задаётся **подзапросом**, не `IN` со списком тысяч
  идентификаторов: планировщик получает константы вместо отношения и не может
  воспользоваться индексом;
* порядок — **сначала дети, потом родители**;
* долгие операции запускаются отвязанными от сессии: обрыв SSH оставляет живую
  транзакцию, которая держит блокировки и не завершается никогда.
