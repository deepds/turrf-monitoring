## 0. Решение о масштабе переработки

**Вывод Phase 0: крупная переработка обоснована, но не является переписыванием
с нуля.**

Обоснование по пунктам:

1. **Модель данных заменяется** — потому что заменился предмет наблюдения:
   1703 редактируемых сценария против детерминированной матрицы из 15 840
   наблюдений, вычисляемой функцией от даты.
2. **Collection Engine заменяется** — потому что заменилась единица работы:
   сценарий в часовом окне против логического наблюдения рынка за сутки.
3. **Коннекторы перерабатываются** — потому что **изменился источник**: Туту
   0.32 отдаёт категорию вагона из поиска, а карта мест, на которой держалась
   вся ЖД-логика v1, больше не нужна и вредна (предкорзинные цены).
4. **Витрина и фронтенд заменяются** — потому что заменились экраны: пять
   экранов SCOPE-R P21 против семнадцати страниц исследовательского стенда.
5. **Правила надёжности переносятся дословно** — потому что они защищают от
   конкретных инцидентов, а не от гипотез.

Репозиторий отдельный (`turrf_monitoring`), стек v1 на node67 остаётся
работающим: его исторические raw-ответы и Offers — evidence, а не мусор.

## 2. Порядок работ и зависимости

```text
Phase 0 (аудит)
   ↓
Phase 1 (модель + сбор) ──┐
   ↓                      │
Phase 2 (методика)        │  Phase 4 (тесты) идёт параллельно с 1–3:
   ↓                      │  каждый закрытый дефект сразу становится
Phase 3 (API + UI) ───────┘  regression-тестом
   ↓
Phase 5 (пилот)
```

Правило, вынесенное из v1: **каждый критичный дефект, способный дать
неправильную цифру, превращается в regression-тест в тот же день**, а не
попадает в список «надо бы покрыть».

## 3. Решения, зафиксированные Phase 0

| Решение | Значение | Обоснование |
|---|---|---|
| Одновременность Туту | 8 | При 12 получен `503` и размыкатель унёс 343 наблюдения |
| Темп Туту | 240/мин | Совпадает со средним темпом суточного цикла; всплески сглаживает лимитер |
| Одновременность РЖД | 4 | Двухфазный протокол дороже одного HTTP-запроса; замер под нагрузкой не проводился |
| Глубина пагинации | полная (10 страниц) | Сокращение до 3 экономит треть цикла и делает 62,5 % авиаметрик смещёнными |
| Мягкий бюджет пачки | 240 с при жёстком 300 с | Жёсткий обрыв уничтожает уже собранное |
| Порог READY | 0,98 | Прогон, потерявший больше 5 %, должен быть виден; 2 % — запас на неизбежные отказы |
| Порог DEGRADED | 0,85 | Ниже — снимок описывает не рынок, а его часть неизвестного состава |
| `min_data_share` | 0,50 | Предохранитель от «покрытие 100 %, цифр нет» при сломанном разборе |
| Целевая выборка ЖД | 6 | На направлении ходит 2–15 поездов; требовать 30 значило бы объявить исправное наблюдение плохим |
| Целевая выборка авиа | 12 | После схлопывания тарифной сетки остаётся 10–40 рейсов |
| Целевая выборка отелей | 25 | Выдача упирается в потолок 200; 25 — уверенно достижимый минимум |
| Порог чистки выбросов | 8 наблюдений | Ниже — «выброс» есть половина рынка направления |
| Ретеншен тел сырых ответов | 45 суток | Полтора месяца на расследование; метаданные и Offers не удаляются |

## 4. Риски и что с ними делать

| Риск | Вероятность | Что делаем |
|---|---|---|
| Источник нестабилен по латентности (замер: пятикратный разброс) | Высокая | Окна расписания шире ожидаемой длительности; 14 часов запаса после 10:00; досбор штатный |
| Источник меняет схему инструмента | Средняя | Имена и границы читаются из `tools/list`; несовпадение даёт `SCHEMA_ERROR`, а не пустую выдачу |
| Перегрузка источника нашим темпом | Средняя | Лимитер + размыкатель + консервативная одновременность; soak-прогон до эксплуатации |
| Объём `offers` (до 5,2 млн строк в сутки) | Средняя | Пакетная вставка; ретеншен тел; партиционирование — при выходе за 30 суток истории |
| РЖД недоступен с части сети | Подтверждено | Сбор выполняется только на узле кластера; проверка `check-sources` перед прогоном |
| Витрина показывает вчерашние данные как сегодняшние | Низкая | Архитектурно закрыто: `is_fallback` в контексте, баннер на каждом экране |
