# Перенос снимков между стендами

Снимок, собранный на одном стенде, переносится на другой и показывается там как
отдельная **версия** своей даты: v1, v2. Собранное здесь при этом не
подменяется — обе версии видны, и выбор между ними принадлежит человеку.

Перенос идёт файлами через репозиторий и разворачивается руками. Прямого
соединения между стендами не требуется и не предполагается.

---

## Главное в трёх утверждениях

1. **Скопировать строки нельзя.** Первичные ключи на приёмнике заняты своими, и
   загрузка переназначает все идентификаторы по карте «старый → новый».
2. **Полный снимок в git не проходит.** Предложения одного снимка — это сотни
   мегабайт. Уровень `showcase` умещается в единицы, но платит раскрытием цифры
   до конкретного предложения.
3. **Снимок из чужой методики не грузится.** Загрузка останавливается, а не
   подставляет активную: цифры остались бы прежними, а объяснение к ним чужим.

---

## Два уровня и чем они отличаются

Замер на полной матрице 15 840 наблюдений (meduza, 08.08.2026):

| Уровень | Что внутри | Размер | Время | Раскрытие цифры |
|---|---|---:|---:|---|
| `showcase` | снимок, план, наблюдения, попытки, расчёт, метрики, витрина поездок, сводка источников | **5,8 МБ** | 8 с | **не работает** |
| `evidence` | плюс `offers` (440 538), `raw_responses`, `metric_offer_links` (440 538) | **54 МБ** | 1 мин 39 с | работает |

Крупнейший файл уровня `evidence` — `offers.ndjson.gz`, 42 МБ: в лимит GitHub
на файл (100 МБ) он укладывается, и разовый перенос через репозиторий возможен.

**Ограничение не в размере файла, а в накоплении.** История git хранит каждую
версию навсегда: 54 МБ в сутки — это 20 ГБ в год, и платит за них каждый, кто
клонирует репозиторий. Даже `showcase` даёт 2 ГБ в год. Поэтому ежедневный
поток — `showcase`, а `evidence` переносится выборочно и лучше Release-ассетами
или LFS, где история не тянется в клон.

Загрузка `showcase` полной матрицы занимает 20 секунд.

**Снимок уровня `showcase` помечен `evidence_included = false`,** и витрина
обязана это показывать. Без пометки пустой список предложений читается как
дефект расчёта, а не как отсутствие переноса.

## Как выгрузить

```bash
docker compose exec api python -m tmo.cli export-snapshot \
  --snapshot-date 2026-08-09 --level showcase --stand node67 --out /var/tmo/export
```

Получается каталог с `manifest.json` и по файлу NDJSON.gz на таблицу. Манифест
несёт версию формата, дату, попытку, версию методики, число строк и sha256
каждого файла, а также `content_digest` — отпечаток содержимого целиком.

Формат — NDJSON, а не SQL-дамп: дамп привязан к версии схемы и к именам
последовательностей, а грузить надо в живую базу, у которой уже есть свои
снимки.

## Как загрузить

```bash
docker compose exec api python -m tmo.cli import-snapshot /var/tmo/import/2026-08-09
```

Загрузка проверяет по порядку и останавливается на первом несовпадении:

| Проверка | Почему отказ, а не умолчание |
|---|---|
| версия формата | загрузка обязана отказаться от того, чего не понимает |
| sha256 каждого файла | частично загруженный снимок хуже отсутствующего |
| методика зарегистрирована | чужое объяснение к правильным цифрам — худший исход |
| `content_digest` не встречался | тот же файл дважды не создаёт вторую версию |

---

## Что происходит с идентификаторами

Порядок загрузки — порядок зависимостей: ребёнок не пишется раньше родителя.
Таблицы, на которые кто-то ссылается, вставляются с возвратом идентификаторов;
порядок возврата задаётся явно (`sort_by_parameter_order`).

**Это не перестраховка.** Без явного порядка соответствие «старый → новый»
держалось бы на неоговорённом поведении СУБД, и карта однажды перемешалась бы
молча — с предложениями, привязанными к чужим наблюдениям. Цифры при этом
остались бы правдоподобными.

Ссылка на строку, которая не переносилась (уровень `showcase` не тащит
предложения, а на них ссылается `raw_response_id`), обнуляется. Ссылка на чужую
строку хуже отсутствующей.

### Ключ идемпотентности

`idempotency_key` уникален по всей базе, а собирается из даты снимка,
наблюдения, источника и области исполнения — и ничего не знает о том, кто
собирал. **Два стенда, собравшие одну дату, порождают побайтово одинаковые
ключи**, поэтому загрузка снимка с соседнего стенда упирается в уникальность
даже на чистой базе.

Ключи загруженной попытки уходят в пространство имён отпечатка выгрузки. Смысл
ключа не теряется: он защищает от повторной записи попытки внутри одного
прогона, а прогон, породивший эти попытки, шёл на другом стенде и здесь не
повторится.

### Номер попытки

Исходный номер сохранить нельзя: он занят снимком, собранным здесь, а
уникальность пары «дата + попытка» держит база. Загрузка берёт следующий
свободный — отсюда и берутся v1, v2 на витрине.

## Порядок работы через репозиторий

```bash
# На стенде-источнике
docker compose exec api python -m tmo.cli export-snapshot \
  --snapshot-date 2026-08-09 --level showcase --stand node67 --out /var/tmo/export
docker compose cp api:/var/tmo/export/2026-08-09 ./snapshots/2026-08-09

# В репозитории снимков
git add snapshots/2026-08-09 && git commit -m "Снимок 2026-08-09 с node67" && git push

# На стенде-приёмнике
git pull
docker compose cp ./snapshots/2026-08-09 api:/var/tmo/import/2026-08-09
docker compose exec api python -m tmo.cli import-snapshot /var/tmo/import/2026-08-09
```

Приёмнику нужна схема не старее выгрузки: миграция `c7d2f1a83b45` добавляет
поля перенесённого снимка. Она применяется сама при запуске контейнера `api`.

**Обратной совместимости у миграций нет.** Стенд, работающий на старом коде, не
запустится после того, как к его базе применили новую ревизию: alembic не
найдёт её в своём каталоге. Обновлять код и схему надо вместе.

---

## Чего этот перенос не делает

- **Не переносит тела сырых ответов.** Метаданные `raw_responses` уровень
  `evidence` несёт, сами файлы лежат в томе `raw_storage` и копируются
  отдельно, если нужны.
- **Не сливает две версии в одну.** Две попытки одной даты остаются двумя
  снимками. Сравнивать их — работа человека, и витрина даёт для этого селектор
  версии.
- **Не проверяет, что цифры сошлись.** Совпадение расчётов двух стендов —
  вопрос приёмки, а не переноса.
